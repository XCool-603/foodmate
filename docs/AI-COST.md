# 美食伴侣 · AI 依赖与成本

> 结论先说：**不接 AI 也能用**，而且能用的部分是绝大部分。
> 只有 3 个功能需要 AI，且每个都有降级路径。

---

## 一、哪些功能依赖 AI

代码里 `IVisionModelClient` / `ITextModelClient` 只在**三个**端点被调用：

| 端点 | 功能 | 用哪个模型 | 不接 AI 时 |
|---|---|---|---|
| `POST /ai/recognize` | 拍照识别菜品 | 视觉模型 | 回落到**手动记录**（记录页本来就有入口） |
| `POST /ai/recipe` | 生成菜谱 | 文本模型 | 显示「这道菜还没有做法」；**301 道菜里有 124 道本来就带菜谱** |
| `POST /ai/shopping-list` | 生成买菜清单 | 文本模型 | 食材清单直接从数据库读，不需要 AI |

**除此之外，全部不依赖 AI**：

| 功能 | 实现方式 |
|---|---|
| **七维决策引擎** | 纯算法（加权打分 + 硬过滤 + 乘性惩罚），零外部依赖 |
| **口味画像** | 纯统计算法（从历史记录反推辣度/预算/菜系） |
| **连续打卡** | 纯日期计算 |
| **记录 / 统计 / 数据看板** | 纯数据库查询 + 聚合 |
| **301 道菜品库** | 静态种子数据（JSON 内嵌在程序集里） |
| **抽卡演出 / 对话流程** | 纯前端动画 + 决策接口 |
| **认证 / 多端登录** | JWT + 各平台开放接口 |

### 换句话说

**AI 是「锦上添花」，不是「地基」。** 拿掉 AI，这个 App 的核心闭环依然完整：

```
和角色对话 → 决策引擎打分 → 抽卡 → 看食材和做法 → 记录 → 画像变准 → 下次更准
                                                    ↑
                                          这条链上只有「拍照」是可选的
```

## 二、当前默认状态：本地桩（免费）

`appsettings.json` 里默认是：

```json
"Ai": { "Provider": "Stub" }
```

**桩模型 = 本地假模型**：

- 不联网、不花钱、离线可用
- 返回**确定性的模板内容**（例如菜谱永远是「备齐食材 → 热锅冷油 → 下主料翻炒…」）
- **响应里 `isStubModel: true`，前端会明确提示用户**——不假装是真 AI

你现在看到的就是这个状态。所以**目前一分钱没花**。

## 三、接真 AI 的成本结构

### 3.1 计费方式

所有主流大模型都按 **token** 计费（输入 + 输出分开算）：

| 调用类型 | 主要消耗 | 量级 |
|---|---|---|
| **视觉识别**（一张图） | 图片转成 token（通常 1000–2000）+ 提示词 + 输出 | 单次约 **¥0.01–0.05** |
| **菜谱生成** | 提示词 + 输出（约 500–1500 token） | 单次约 **¥0.002–0.01** |

> ⚠️ **具体单价请按你选定模型当时的官方价目核实。** 上面是量级参考，
> 不同厂商（通义/豆包/DeepSeek/OpenAI）差好几倍，且经常调价。

### 3.2 代码里已经内置的限流

`AiOptions.cs` 里已经写死了配额，这是**成本的天花板**：

```csharp
RecognizePerHour = 20      // 每用户每小时最多识别 20 次
RecognizePerDay  = 100     // 每用户每天最多识别 100 次
RecipePerDay     = 30      // 每用户每天最多生成 30 份菜谱
MaxImageBytes    = 5MB     // 图片大小上限
```

### 3.3 按限流算最坏情况

假设 **1000 个日活用户**，且**每个都跑满配额**（现实中不可能）：

| 项目 | 计算 | 单日调用量 |
|---|---|---|
| 识别 | 1000 × 100 | 100,000 次 |
| 菜谱 | 1000 × 30 | 30,000 次 |

按上表量级估算：

```
识别  100,000 × ¥0.02  = ¥2,000/天
菜谱   30,000 × ¥0.005 = ¥  150/天
                         ─────────────
                          ¥2,150/天  ≈ ¥64,500/月
```

**这是「所有人都跑满配额」的理论上限**，实际远低于此。

### 3.4 更现实的情况

真实用户不会每天识别 100 张照片。按**合理使用**估：

| 场景 | 日活 | 人均识别/天 | 日成本 | 月成本 |
|---|---|---|---|---|
| 内测 | 20 | 3 | ≈ ¥1.2 | ≈ ¥36 |
| 小规模 | 200 | 3 | ≈ ¥12 | ≈ ¥360 |
| 有起色 | 2,000 | 3 | ≈ ¥120 | ≈ ¥3,600 |
| 火了 | 20,000 | 3 | ≈ ¥1,200 | ≈ ¥36,000 |

> 按「人均 3 次识别 + 1 次菜谱」估，**单用户单日成本约 ¥0.06**。

## 四、省钱手段（代码里已经做了几个）

| 手段 | 状态 | 说明 |
|---|---|---|
| **桩模型兜底** | ✅ 已实现 | 没配 Key 就用模板，功能不中断、不花钱 |
| **菜谱落库复用** | ✅ 已实现 | 生成过的菜谱存进 `recipes` 表，**同一道菜第二次不再调模型** |
| **修正数据沉淀** | ✅ 已实现 | 用户纠正的识别结果存进 `corrected_result`，作为后续优化素材 |
| **配额限流** | ✅ 已实现 | 每用户每小时/每天上限，防止被刷 |
| **图片大小限制** | ✅ 已实现 | 5MB 上限，避免超大图烧 token |
| **模型可切换** | ✅ 已实现 | 改配置就能从贵模型换到便宜模型，代码零改动 |
| **按需生成** | ✅ 已实现 | 菜谱只在用户点「生成菜谱」时才调，不预生成 301 道 |
| **降级为手动** | ✅ 已实现 | AI 不可用时前端直接给手动入口，不是死路 |

### 还没做但可以做的

| 手段 | 效果 |
|---|---|
| **本地视觉模型**（Ollama + Qwen2.5-VL） | **零边际成本**，但需要一台带 GPU 的服务器（约 ¥1,000–3,000/月） |
| **图片压缩后再送模型** | 长边压到 1024px，token 消耗可降 50%+ |
| **识别结果缓存** | 同一张图（按哈希）不重复识别 |
| **分档限流** | 免费用户 5 次/天，付费用户不限 |
| **便宜模型打底 + 贵模型兜底** | 先用便宜模型，置信度低时才升级 |

## 五、给你的建议

### 短期（内测阶段）

**继续用桩模型，一分钱不花。**

现在该验证的是「决策引擎准不准」「抽卡体验好不好」——这两件事**跟 AI 完全无关**。
等有真实用户了，再决定要不要开 AI。

### 中期（有几十个真实用户）

**开文本模型，先不开视觉模型。**

- 菜谱生成便宜（¥0.005/次），能明显提升「自己做」模式的体验
- 拍照识别贵 4–10 倍，而且**当前 301 道菜没有真实照片**，
  用户拍的照片能不能被准确识别，需要真实数据验证

配置示例：

```bash
Ai__Provider=OpenAiCompatible
Ai__BaseUrl=https://dashscope.aliyuncs.com/compatible-mode/v1
Ai__ApiKey=<你的密钥>
Ai__TextModel=deepseek-chat        # 便宜
```

### 长期（用户量上来了）

- **上本地视觉模型**——边际成本归零，但要算服务器账
- 或者**识别走便宜的视觉模型**（如通义 qwen-vl-plus 而非 max）

---

## 六、一句话总结

> **不接 AI，这个 App 95% 的功能照常工作**（决策、记录、画像、看板、301 道菜、抽卡）。
> 接 AI 只影响「拍照识别」和「生成菜谱」两件事，成本**完全可控**——
> 代码里的配额限流就是成本天花板，而且**改一行配置就能随时关掉**。
