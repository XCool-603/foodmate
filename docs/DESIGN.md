| 项目 | 内容 |
|---|---|
| 文档版本 | v1.0 |

## 1. 产品定义

### 1.1 一句话定位

> **一个帮你不假思索决定「今天吃什么」，并顺手记住你吃了什么的美食伴侣。**

### 1.2 目标用户

| 用户画像 | 场景 | 核心诉求 |
|---|---|---|
| 上班族（主力） | 每天 11:30 / 18:00 的决策瘫痪 | 「别让我想，直接给我一个答案」 |
| 独居青年 | 一个人吃饭，懒得规划 | 「别总让我吃那几样，但也别太离谱」 |
| 减脂/健身人群 | 想控制饮食但懒得算 | 「拍一张就知道吃了多少」 |
| 情侣/室友 | 两个人互相推诿「你定」 | 「给个第三方裁决」 |

### 1.3 核心价值主张

现有产品（大众点评、美团、下厨房、薄荷健康）都是 **搜索 / 浏览** 逻辑——你必须先知道自己想要什么，或者愿意花时间逛。

**没有人做「帮你不假思索地决定」。**

美食伴侣的价值链：

```
降低决策成本  →  降低记录成本  →  形成口味画像  →  决策更准
   （拉新）         （留存）         （护城河）      （复利）
```

### 1.4 明确不做的事（个人主体约束下的主动收缩）

> ⚠️ 这是本项目的**红线**，所有后续设计都必须遵守。

| 不做 | 原因 |
|---|---|
| ❌ 外卖下单 / 跳转外卖平台 | 涉及交易与导流，个人主体类目几乎不可能过审 |
| ❌ 团购券 / 优惠券 / 返佣 | 同上，且涉及资金 |
| ❌ 商家入驻 / 点评打分公开体系 | 涉及 UGC 内容审核责任与经营资质 |
| ❌ 支付功能 | 个人主体小程序无微信支付权限 |
| ❌ 广告变现（v1） | 需要流量门槛，且影响体验 |

**产品定位必须严格保持在「工具」范畴**：帮你决定、帮你记录、帮你了解自己。
不碰交易，就不碰资质。

> 📌 **待核实**：各平台对「美食/餐饮」类目的具体资质要求会随政策调整，上线前请以微信/支付宝/抖音开放平台**当前官方口径**为准。本设计已按最保守假设（个人主体、无资质）规划。

### 1.5 竞品差异

| 产品 | 逻辑 | 美食伴侣的差异 |
|---|---|---|
| 大众点评 | 搜索 + 榜单 | 我们不做「找店」，做「替你做决定」 |
| 美团 | 交易 | 我们不做交易 |
| 下厨房 | 菜谱浏览 | 我们把菜谱作为「自己做」模式的一个分支 |
| 薄荷健康 | 严格卡路里 | 我们**不苛责**，只呈现不批判，避免用户因负罪感流失 |

## 2. 产品闭环

### 2.1 三大闭环

```
┌─────────────────────────────────────────────────────────┐
│  闭环 A：决策（拉新 + 高频）                              │
│                                                          │
│   打开 → 选模式 → 「帮我决定」 → 转盘 → 结果 → 就吃这个    │
│                          ↑                    │          │
│                          └──── 打分引擎 ←──────┘          │
└─────────────────────────────────────────────────────────┘
                              ↓ 沉淀
┌─────────────────────────────────────────────────────────┐
│  闭环 B：记录与画像（留存 + 护城河）                      │
│                                                          │
│   就吃这个 → 自动生成记录 → 事后评分 → 更新画像 → 决策更准 │
└─────────────────────────────────────────────────────────┘
                              ↑ 补充
┌─────────────────────────────────────────────────────────┐
│  闭环 C：AI 拍照（降低记录门槛）                          │
│                                                          │
│   拍照 → 视觉模型识别 → 用户确认/修正 → 入库 → 沉淀菜品库  │
└─────────────────────────────────────────────────────────┘
```

**闭环之间的关键连接点：**

- **A → B**：结果页的「就吃这个」一键创建记录，**不跳表单**。这是留存的关键——记录必须零摩擦。
- **B → A**：记录产生的评分（`Rating`）和「还想再吃」（`WouldEatAgain`）是决策引擎最强的信号。
- **C → B**：AI 识别把「记录」的成本从「打字搜索」降到「拍一张 + 点确认」。
- **C → 数据资产**：用户对 AI 结果的**修正**是最有价值的数据，反哺菜品库。

### 2.2 关键用户旅程

**旅程 1：新用户首次使用（目标：60 秒内出结果）**

```
扫码进入 → 3 屏价值主张（可跳过）
        → 5 道偏好题（辣度/预算/忌口/菜系/就餐方式）
        → 直接进入决策页（画像已就绪，无需空等）
        → 「帮我决定」→ 转盘 → 结果
```

**旅程 2：日常高频使用（目标：10 秒内出结果）**

```
打开小程序 → 首页已根据时段/天气预填好条件
          → 点「帮我决定」→ 转盘 2 秒 → 结果
          → 「就吃这个」→ 完成
```

**旅程 3：吃完回来记录（目标：3 次点击）**

```
拍一张照片 → 上传识别（~3 秒）→ 确认结果 → 打分 → 完成
```

**旅程 4：晚上想自己做**

```
决策页选「自己做」→ 推荐快手菜 → 结果页展示菜谱
                → 「买菜清单」→ 复制/分享 → 完成
```

### 3.2 MVP 边界（M0–M3，约 3 周）

**必须有**：决策闭环完整可用、记录可增删改查、画像可编辑、AI 拍照能识别入库。
**可以粗糙**：UI 视觉、动画精致度、错误文案、菜品种子数据量（先 300 道够用）。
**不做**：社区、评论、积分、成就系统、多语言、深色模式、离线包。

### 4.2 页面详细设计

#### 4.2.1 决策页（首页）`/pages/decide/index`

**布局（从上到下）**

```
┌──────────────────────────────────┐
│  中午好 👋                        │  ← 时段问候（6-10早/11-14午/17-21晚/其余夜宵）
│  该吃午饭了，今天想吃点什么？      │  ← 天气融入（"外面在下雨"）
├──────────────────────────────────┤
│  ┌──────┬──────┬──────┬──────┐   │
│  │ 外卖 │ 堂食 │自己做│ 随便 │   │  ← 就餐模式，单选，默认「随便」
│  └──────┴──────┴──────┴──────┘   │
├──────────────────────────────────┤
│  预算   ¥15 ────●────── ¥80      │  ← 滑块，默认取画像区间
│  人数   [1人] [2人] [3-4人] [更多]│
│  想吃点 辣的 清淡 暖胃 快手 随便   │  ← 快捷标签，多选，可空
├──────────────────────────────────┤
│                                  │
│      ╭────────────────────╮      │
│      │   帮我决定 🤔       │      │  ← 主 CTA，大按钮
│      ╰────────────────────╯      │
│                                  │
├──────────────────────────────────┤
│  或者：直接转个盘 →               │  ← 次级入口，跳过条件
└──────────────────────────────────┘
```

**交互要点**

- 页面加载时**异步预取**候选菜品（Top 50），点击 CTA 时本地已就绪 → 感知延迟 < 200ms。
- 天气与定位**不阻塞**首屏：先出界面，权限弹窗在用户点击 CTA 时才请求。
- 所有条件**都有默认值**，用户一个都不改也能直接点 CTA。
- 「帮我决定」与「直接转个盘」的区别：前者走完整打分，后者跳过条件用默认画像。

**状态**

| 状态 | 表现 |
|---|---|
| 首次进入（无画像） | 引导做偏好题，CTA 文案改为「先告诉我你的口味 →」 |
| 定位权限被拒 | 静默降级，不显示距离维度，不弹二次请求 |
| 网络失败 | 使用上次缓存的候选集，顶部提示「离线推荐」 |

#### 4.2.2 结果页 `/pages/decide/result`

**布局**

```
┌──────────────────────────────────┐
│  ← 返回        为你挑了 8 道      │
├──────────────────────────────────┤
│                                  │
│         ╭────────────╮           │
│         │   转盘      │           │  ← Canvas 绘制，8 等分扇区
│         │  (8 道菜)   │           │     每扇区显示菜名（≤4 字）
│         ╰────────────╯           │
│                                  │
│      ╭────────────────╮          │
│      │    开始转 🎯    │          │
│      ╰────────────────╯          │
├──────────────────────────────────┤
│  为什么是这些？                    │
│  ┌────────────────────────────┐  │
│  │ 1. 番茄牛腩      92 分      │  │  ← Top 榜，默认展示 5 条
│  │    你最近吃辣偏多，换点温和的 │  │  ← 推荐理由（人话）
│  │    ¥38 · 川菜 · 微辣        │  │
│  │                    [详情 ▾] │  │
│  ├────────────────────────────┤  │
│  │ 2. 清蒸鲈鱼      88 分      │  │
│  │    上次你给它打了 5 分       │  │
│  └────────────────────────────┘  │
│                                  │
│         [ 换一批 ]                │
└──────────────────────────────────┘
```

**转盘交互细节**

- **扇区等分**（不做加权扇区）。理由：加权扇区用户感知不公平，且小程序 Canvas 绘制复杂、难以解释。分数差异通过「只放 Top 8」来体现。
- 旋转动画 **1.8 秒**，缓出（`easeOutCubic`）。超过 2.5 秒用户会不耐烦。
- 停止后：高亮该扇区 + 震动反馈（`wx.vibrateShort`）+ 自动滚动到 Top 榜中对应项。
- 转盘结果**不强制**。用户可「再转一次」或直接从榜单选。
- 转盘与榜单**同源**：都来自 Top 8，保证一致性。

**操作按钮**

| 按钮 | 行为 |
|---|---|
| 就吃这个 | 创建 `MealRecord`（含 `DecisionSessionId`）→ Toast → 跳记录页 |
| 换一批 | 重新调用 `/decisions/suggest`，排除本次已出现的菜品 |
| 分享 | 生成图片卡片（转盘结果 + 推荐理由 + 小程序码） |
| 为什么推荐 | 展开打分明细条形图 |

**关键设计：可解释性**

每个推荐**必须**给出人话理由。理由由打分明细自动生成，取**贡献最大的 2 个维度**：

| 贡献维度 | 文案模板 |
|---|---|
| 口味匹配高 | 「你爱吃{菜系}，这道很对味」 |
| 新鲜度加成 | 「你最近 {n} 天吃了 {m} 次{菜系}，今天换个花样」 |
| 偏好强度高 | 「上次你给它打了 {rating} 分」 |
| 时段契合 | 「{早/午/晚}餐吃这个正合适」 |
| 预算匹配 | 「¥{price}，在你的预算内」 |
| 天气契合 | 「{下雨/降温}天，来点{热乎的/清淡的}」 |
| 探索加成 | 「你没试过这道，要不要尝尝」 |

> 💡 **这是本产品的差异化核心**。用户不信任黑盒推荐。给出理由 = 建立信任 = 提升采纳率。

#### 4.2.4 AI 拍照识别 `/pages/ai/recognize` + `/pages/ai/confirm`

```
[recognize]                        [confirm]
┌────────────────────┐            ┌────────────────────┐
│  ← 拍照识别         │            │  识别到 3 道菜      │
│                    │            │                    │
│  ┌──────────────┐  │            │ ┌────────────────┐ │
│  │              │  │            │ │[缩略图] 番茄牛腩 │ │
│  │   相机预览    │  │            │ │ 置信度 92%      │ │
│  │              │  │            │ │ 份量 [1份 ▾]    │ │
│  └──────────────┘  │            │ └────────────────┘ │
│                    │            │ ┌────────────────┐ │
│  ╭──────────────╮  │            │ │[缩略图] 米饭    │ │
│  │ 拍照 / 相册   │  │            │ │ 置信度 61% ⚠️   │ │
│  ╰──────────────╯  │            │ │ ← 低置信度标黄  │ │
│                    │            │ │ 份量 [1碗 ▾]    │ │
│                    │            │ └────────────────┘ │
│                    │            │                    │
│                    │            │ [+ 手动添加一道]    │
│                    │            │                    │
│                    │            │ ╭────────────────╮ │
│                    │            │ │   确认并记录    │ │
│                    │            │ ╰────────────────╯ │
└────────────────────┘            └────────────────────┘
```

**识别流程**

```
1. 用户拍照/选图
2. 前端压缩（长边 ≤ 1280px，质量 80%）→ 体积 ≤ 500KB
3. 上传到对象存储 → 拿到 URL（或直传后端）
4. POST /ai/recognize { imageUrl }
5. 后端调用视觉模型，返回结构化 JSON
6. 前端展示确认页，低置信度项（< 70%）标黄并置于顶部
7. 用户确认/修正 → POST /ai/recognize/{logId}/confirm
8. 后端：创建 MealRecord + 沉淀修正数据
```

**关键设计决策**

| 决策 | 理由 |
|---|---|
| **必须让用户确认，绝不直接入库** | 视觉模型准确率有限，直接入库会污染数据、伤害信任 |
| **低置信度标黄并置顶** | 引导用户优先修正最可能错的地方 |
| **识别 + 修正都记录到 `AiRecognitionLog`** | 修正数据是训练/优化的黄金数据 |
| **识别失败不报错，降级为手动输入** | AI 是增强不是依赖 |
| **一次识别多道菜** | 一顿饭通常多个菜，逐张拍体验差 |

**上传优化**

- 前端压缩后再传，避免 5MB 原图上传等待。
- 上传用 `uni.uploadFile`，显示真实进度条。
- 识别中展示骨架屏 + 趣味文案（「正在努力辨认…」），避免干等。

#### 4.2.5 我的 / 口味画像

**我的页**：数据卡片（累计记录 / 尝试菜品数 / 连续打卡）+ 画像入口 + 设置。

**口味画像页**：

| 字段 | 控件 | 影响 |
|---|---|---|
| 辣度偏好 | 0–5 滑块 | `TasteScorer` |
| 每餐预算 | 双滑块区间 | `BudgetScorer` |
| 忌口 / 过敏 | 多选标签（含自定义输入） | **硬过滤**，直接排除 |
| 偏好菜系 | 多选（8 大菜系 + 其他） | `TasteScorer` |
| 就餐方式偏好 | 外卖/堂食/自己做 排序 | `ContextScorer` |

> ⚠️ **忌口是硬约束，不是打分项。** 用户勾选「花生过敏」后，含花生的菜品必须**完全不出现在候选集**，而不是分数低。这是安全问题，不可妥协。

### 5.4 关键设计决策（ADR）

#### ADR-001：数据库双 Provider（SQLite 开发 / PostgreSQL 生产）

**背景**：本机未安装 Docker，直接跑 PostgreSQL 有额外成本。

**决策**：开发环境用 SQLite，生产用 PostgreSQL，通过 `appsettings.json` 的 Provider 配置切换。

**约束**：
- ❌ 禁止使用数据库特有功能（PostgreSQL 的 `jsonb` 运算符、`ILIKE`、数组类型等）
- ✅ JSON 字段统一存为 `string`，用 EF Core `ValueConverter` 或 Owned Entity 序列化
- ✅ 字符串比较统一用 `EF.Functions.Like`，避免大小写敏感差异
- ✅ 所有查询必须在两个 Provider 上都能跑通

**代价**：放弃部分 PostgreSQL 性能优势。**收益**：零配置开发，CI 无需容器。

#### ADR-002：决策引擎放在 Core 层，纯函数式，不依赖数据库

**决策**：`DecisionEngine` 接收 `(候选菜品列表, 用户画像, 用户历史统计, 决策请求)`，返回打分结果。**不注入 DbContext**。

**理由**：
- 可单元测试（这是本项目最需要测试的部分）
- 打分逻辑是产品核心资产，必须与存储解耦
- 便于将来把候选集换成向量检索 / 外部数据源

#### ADR-003：忌口用硬过滤而非扣分

**决策**：忌口/过敏命中 → 候选集中**直接移除**。

**理由**：这是安全问题。分数低仍可能被转盘抽中（转盘只取 Top 8，但若候选集小则可能漏入）。

#### ADR-004：转盘等分扇区

**决策**：Top 8 等分扇区，不做概率加权。

**理由**：加权扇区（扇形面积 ∝ 分数）在小程序 Canvas 上绘制复杂，且用户直觉上认为「转盘 = 公平随机」，面积不等会引起困惑。分数差异通过「只放 Top 8」体现，已足够。

#### ADR-005：AI 结果必须用户确认

**决策**：`/ai/recognize` 只返回结果并写日志，**不创建记录**；用户调 `/ai/recognize/{logId}/confirm` 后才入库。

**理由**：视觉模型准确率不足以直接信任；修正数据是核心数据资产。

#### ADR-006：多端差异全部收敛到 `platform/` 适配层

**决策**：业务代码中**零 `#ifdef`**。所有平台差异通过 `platform/index.ts` 的条件导入 + 统一接口暴露。

**理由**：`#ifdef` 散落会导致三端行为不一致、难以测试、新人无法理解。

#### ADR-007：共享基元放在 Core，而非 Contracts（M0 实施时确定）

**背景**：原计划把所有「前后端共享 DTO」放进 `FoodMate.Contracts`。但实施时发现
`ApiResponse<T>`、`PagedResult<T>`、`ApiErrorCode` 是**框架级基元**——
`BusinessException` 需要携带 `ApiErrorCode`，而 `BusinessException` 属于 Core。

**决策**：
- `FoodMate.Core` 持有：`ApiResponse<T>`、`PagedResult<T>`、`ApiErrorCode`、`BusinessException`、`EnumLabels`
- `FoodMate.Contracts` 持有：**业务** DTO（`DishBriefDto`、`MetaDtos` 等），依赖 Core

**理由**：若把这些基元放进 Contracts，则 Core 必须依赖 Contracts，而 Contracts 又依赖 Core
（业务 DTO 需要引用领域实体做投影），形成循环依赖。

**代价**：Core 不再「纯粹」——含少量 API 契约概念。**收益**：依赖图无环，且业务逻辑可直接抛出带错误码的异常。

## 7. 数据与安全

### 7.1 认证与授权

- **Token 方案**：Access Token（有效期 2 小时，JWT）+ Refresh Token（有效期 30 天，存库可撤销）。
- **存储**：小程序端用 `uni.setStorageSync` 存 token；请求拦截器自动附加 `Authorization: Bearer {token}`。
- **401 处理**：拦截器捕获 401 → 自动用 refresh token 续期 → 重放原请求；续期失败 → 静默重新登录 → 再失败则跳转引导页。
- **JWT 密钥**：存环境变量 / 用户机密（`dotnet user-secrets`），**绝不进仓库**。

### 7.2 大模型调用安全

| 风险 | 对策 |
|---|---|
| API Key 泄露 | Key 只在后端 `appsettings.Production.json` / 环境变量，前端永不接触 |
| 用户刷接口烧钱 | AI 接口按用户限流：**20 次/小时，100 次/天**；超限返回 429 |
| Prompt 注入 | 用户输入（菜名等）做长度限制 + 特殊字符过滤；系统提示与用户输入严格分隔 |
| 响应不可控 | 强制 JSON 输出（`response_format` / 结构化约束），解析失败则重试 1 次后降级 |
| 成本失控 | 记录每次调用的 token 消耗到 `AiRecognitionLog`，可监控可告警 |

### 7.3 图片处理

- **上传限制**：单张 ≤ 5MB，格式白名单 `jpg/jpeg/png/webp`。
- **前端压缩**：长边 ≤ 1280px，质量 80%，目标 ≤ 500KB。
- **存储**：对象存储（COS/OSS），按 `{userId}/{yyyyMM}/{guid}.jpg` 分目录。
- **访问**：私有读 + 临时签名 URL（有效期 1 小时），或 CDN 公开读（菜品图）。
- **清理**：用户删除记录时，照片延迟 7 天删除（防误删）；提供「清除所有照片」入口。

### 7.4 隐私合规

- **最小必要**：定位仅在用户点击 CTA 时请求，且**可拒绝**（降级不影响核心功能）。
- **隐私协议**：首次启动展示《用户协议》与《隐私政策》，明确告知收集定位/照片的用途。
- **数据导出/删除**：提供账号注销与数据删除入口（合规要求）。
- **不收集**：不收集手机号（v1 无此需求）、不收集通讯录、不读取剪贴板。

> 📌 **待核实**：小程序上架的隐私协议备案要求（微信「小程序用户隐私保护指引」）需按当前官方要求填写并审核，请在提审前确认。

```
        HTTPS  ────────►│  Nginx / 网关    │   TLS 终止
                        └────────┬────────┘
                                 ▼
                        ┌─────────────────┐
                        │  FoodMate.Api   │   .NET 10 容器
                        │  (Docker)       │   1–2 实例
                        └────────┬────────┘
                                 ▼
                        ┌─────────────────┐
                        │  PostgreSQL     │   云数据库
                        └─────────────────┘
```

### 8.2 域名与备案（⚠️ 本项目最大的外部依赖）

小程序请求的域名必须 **HTTPS + ICP 备案**。

| 方案 | 微信端 | 支付宝/抖音端 | 成本 | 说明 |
|---|---|---|---|---|
| **A. 自建 + 备案域名** | ✅ | ✅ | 域名 ~50元/年 + 服务器 + 备案 1–2 周 | 三端通用，推荐终态 |
| **B. 微信云托管** | ✅ 免域名白名单配置 | ❌ | 按量计费 | 可作微信端过渡，但三端不通用 |
| **C. 先只做 H5** | — | — | 低 | 无需备案即可内测，但失去小程序流量 |

**建议路径**：先走 **A**，但备案周期长 → **并行**：开发期用本地 + 内网穿透联调，同时启动备案；备案完成前先只跑微信开发者工具（可勾选「不校验合法域名」）。

> 📌 **待核实**：备案流程、云托管对 .NET 容器的支持情况与免费额度，请以云厂商**当前官方文档**为准。本设计不依赖任何特定云厂商。

### 8.3 环境划分

| 环境 | 数据库 | 用途 |
|---|---|---|
| Local | SQLite | 日常开发，零配置 |
| Staging | PostgreSQL（小规格） | 提审前的真机联调 |
| Production | PostgreSQL（主从/备份） | 线上 |

### 8.4 可观测性

- **日志**：Serilog → 控制台 + 文件；结构化日志，含 `TraceId`、`UserId`。
- **健康检查**：`GET /health`（存活）+ `GET /health/ready`（含数据库连通性）。
- **关键指标**：决策请求量、决策耗时 P95、AI 调用成功率与耗时、AI token 消耗。
- **告警**：AI 调用失败率 > 10%、接口 P95 > 2s。

## 9. 里程碑与排期

| 里程碑 | 内容 | 交付物 | 预估 |
|---|---|---|---|
| **M0 骨架** | 解决方案结构、EF Core + SQLite、`/health`、统一响应包装、uni-app 工程 + 3 个 Tab 空页、请求封装、**打通前后端** | 手机上能跑起一个显示后端版本号的页面 | 2–3 天 |
| **M1 决策** | 300 道菜种子数据、画像 CRUD、决策引擎 + 7 个 Scorer + 单测、决策页、结果页、转盘组件 | **能真正用来决定吃什么** | 5–7 天 |
| **M2 记录** | 记录 CRUD、记录页、编辑页、统计接口、我的页、画像自动更新、未评分提醒 | 完整留存闭环 | 4–5 天 |
| **M3 AI** | 视觉模型客户端、上传链路、识别 → 确认流、修正数据沉淀、菜谱生成、买菜清单 | 拍照即记录 | 4–5 天 |
| **M4 多端** | 三端登录打通、platform 适配层、支付宝/抖音分别真机调试、提审材料 | 三端可提审 | 5–7 天 |

**合计约 4–6 周**（单人全职估算，含调试与返工）。

**建议节奏**：M0+M1 完成后先给身边 3–5 个人试用，验证「转盘 + 推荐理由」是否真的降低了决策成本，再决定 M2/M3 的优先级。

## 10. 风险登记册

| # | 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|---|
| R1 | **类目审核不通过**（个人主体） | 中 | 致命 | 严守「工具」定位，不做交易/导流；准备 H5 版兜底；提审前先查最新类目要求 |
| R2 | **备案周期超预期** | 高 | 高 | 开发第一天就启动备案；开发期用开发者工具「不校验域名」+ 内网穿透 |
| R3 | **AI 识别准确率低** | 高 | 中 | 强制用户确认；低置信度标黄；降级为手动输入；持续沉淀修正数据 |
| R4 | **菜品种子数据质量差** | 中 | 高 | 人工精选 300 道**高频家常菜**打底，宁少勿滥；不追求覆盖全 |
| R5 | **冷启动无画像导致推荐不准** | 高 | 中 | 5 道偏好题强制引导；无画像时用「大众共识」兜底；转盘保证有输出 |
| R6 | **Node 26 与 uni-app 工具链不兼容** | 中 | 中 | 出现编译问题立即切 Node 22 LTS（volta/fnm 管理） |
| R7 | **三端维护成本失控** | 中 | 中 | 适配层隔离，业务代码零 `#ifdef`；CI 对三端分别构建 |
| R8 | **大模型成本失控** | 中 | 中 | 按用户限流；记录 token 消耗；设置日预算告警 |
| R9 | **用户不愿记录（留存差）** | 高 | 高 | 「就吃这个」一键记录零摩擦；未评分记录主动提醒；AI 拍照降低门槛 |
| R10 | **个人主体无法变现** | 高 | 中 | v1 不考虑变现，专注打磨体验与口碑；后续可升级主体或接合规广告 |
